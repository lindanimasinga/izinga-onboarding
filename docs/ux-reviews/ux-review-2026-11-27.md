## Top 10 fixes (ranked by user impact)

| Rank | Severity | Page | File:Line | Fix | Size |
|---|---|---|---|---|---|
| 1 | Blocker | Phone verification | `phone-verification.component.html:16` | Change `type="text"` → `type="tel" inputmode="tel" autocomplete="tel"` on phone input. Without this, every iOS and Android user sees a QWERTY keyboard instead of the number pad during registration. | S |
| 2 | Blocker | Phone verification | `phone-verification.component.html:36` | Change `type="text"` → `type="text" inputmode="numeric" autocomplete="one-time-code"` on OTP input. Without `autocomplete="one-time-code"`, iOS will not offer to fill the SMS code. Without `inputmode="numeric"`, number pad is not shown. | S |
| 3 | Blocker | User update | `user-update.component.ts` | Add `FixedBarService` injection and call `this.fixedBarService.show()` in `ngOnInit` / `this.fixedBarService.hide()` in `ngOnDestroy`. Without this, `has-fixed-bar` is never added to `body`, so the bottom padding that exposes the last form field and the submit error message (lines 327–329 of the template) is never applied. The fixed-bottom Register/Update button permanently obscures the logout button and any submit error message. | S |
| 4 | Major | User update | `user-update.component.html:231` | The radio for `value="EWALLET"` is labeled `Cash`. eWallet and cash are different payment mechanisms. Drivers selecting this option believe they are opting into a cash payout when they are in fact opting into an eWallet disbursement. Change the visible label to `eWallet`. | S |
| 5 | Major | User update | `user-update.component.html:78,146,195,218,303,313` | Six `<div>` elements carry two `class` attributes: `class="mt-2" class="field-error"`. The browser silently drops the first attribute, so `mt-2` is never applied and field-error messages appear with no top margin, butting directly against the input above them. Merge both attributes: `class="mt-2 field-error"`. | S |
| 6 | Major | Phone verification | `phone-verification.component.html:2` | The `alert alert-warning` div uses Bootstrap's default yellow/amber palette, which renders as a bright yellow box on the iZinga dark surface. Replace with an `iz-notice` or a `field-error`-style div using `var(--btn-amber-color)` and `var(--text-color)` to match the design system. | S |
| 7 | Major | User update | `user-update.component.html:84–91` | Service type ("Tell us about your hustle?") is asked before first and last name (lines 135–149). Standard form UX puts identity fields first. Move the service type select below the name row. For shop accounts, "Account type" appears as the very first question, which is doubly confusing. | M |
| 8 | Major | User management | `user-management.component.html` | Several `<button>` elements that contain only `<i class="fa fa-*"></i>` icon children carry no `aria-label` attribute. Screen-reader users cannot identify these controls. Add `aria-label="Reset search"` (or equivalent) to each icon-only button. | S |
| 9 | Major | User management | `user-management.component.html` | Tab strip uses Bootstrap default `.nav-tabs` with white/light-grey backgrounds (`rgb(255,255,255)` and `rgb(239,239,239)`) on the dark surface. Measured with `getComputedStyle` during visual review. These are Bootstrap-default `.nav-tabs` colors not overridden by iZinga tokens; they appear as bright white pills against the dark background. Replace tab strip styling with the dark-themed pattern from `pending-approvals.component.css` (`color: var(--text-color)`, `border-bottom: 3px solid var(--btn-bg-color)` for active tab). | S |
| 10 | Minor | Phone verification | `phone-verification.component.html:41` | The "To resend click here" row uses `<a>` with no `href`. The click event is on the containing `<div>`, making this unreachable by keyboard Tab navigation. Change to `<button class="btn btn-link p-0" (click)="resend()">Resend code</button>` and remove the outer div's click handler. | S |

## Skill feedback

The mobile-web-ux skill worked well for this review. One area for improvement:

- The skill's responsive-web checklist specifies checking at 360, 768 and 1280px "and in every theme". On pages behind a login wall, this is not achievable without fabricating a session, which the review brief explicitly prohibits. The skill could add a "from code only" fallback procedure for auth-gated pages so reviewers know what to look for in templates without rendering. Currently the reviewer has to improvise that procedure.

- The heuristics.md severity guide is clean and unambiguous; no conflicts with the iZinga design system were encountered. Where the two sources addressed the same question (e.g. `btn-primary` vs `bg-dark`), the iZinga design system takes precedence per the brief.
